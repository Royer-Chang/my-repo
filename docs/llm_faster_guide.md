# 7 種讓 LLM 更快的方法

> 這些技術各自真正做了什麼，更新至 2026 年版本

## 圖片版摘要文字

- 量化：用更低精度數據表示模型，節省記憶體，讓大模型更輕、更快。
- 知識蒸餾：用大模型教小模型，讓小模型學到相似能力，跑得更快。
- 前綴快取：重用相同 prompt 前綴的 KV cache，避免重算。
- 連續批處理：讓 GPU 持續接收新請求，提升整體吞吐量。
- 推測解碼：小模型先猜下一幾個 token，大模型驗證，減少延遲。
- 張量 / 專家並行：把模型分散到多張 GPU 上，同時運算。
- 解耦式服務：把 prefill 和 decode 分開，避免彼此互相拖慢。

## 1) 量化（Quantization）

降低模型精度，以節省記憶體並提升吞吐量。

- FP16 → 16 位元
- FP8 / FP4 → 更低精度
- INT4 / FP4 可在現代 GPU 上更有效率地執行
- 範例：7B 模型以 FP16 運行可能需要約 14 GB，而 FP4 可壓縮到約 3.9 GB

適合使用於：
- 在有限 VRAM 中放入更大的模型
- 減少記憶體瓶頸
- 讓較小 GPU 也能進行推理

## 2) 知識蒸餾（Knowledge Distillation）

讓較小的學生模型模仿較大的教師模型。

- 教師模型產生輸出或分數
- 學生模型學習近似這些結果
- 結果：在更快推理速度下取得較低成本的效果

典型流程：
- 大模型 = 教師
- 小模型 = 學生
- 學生學習複製教師的行為

適合使用於：
- 生產環境中部署輕量模型
- 在維持可接受品質下降低延遲

## 3) 前綴快取（Prefix Caching）

重用先前計算過的 key/value 狀態，避免重複處理相同前綴。

- 系統會為 prompt 前綴儲存 KV cache
- 當新請求共用相同前綴時，不必重新計算
- 對長上下文或重複內容特別有效

核心概念：
- 請求 A 和請求 B 擁有共同前綴
- 快取可重複使用，因此需要的計算更少

適合使用於：
- 多輪對話
- 重複的 system prompt
- 共享前綴的相似 prompts

## 4) 連續批處理（Continuous Batching）

動態將多個請求打包進 GPU batch，以提升利用率。

- GPU 佔位會在請求完成後重新利用
- 新任務會立即填補空閒位置
- 有助於避免閒置，提升整體吞吐量

核心概念：
- 不是固定批次，而是讓 GPU 持續保持忙碌
- 減少浪費的計算，提升系統整體效率

適合使用於：
- 高吞吐量服務
- 大量同時請求
- 生產環境推理系統

## 5) 推測解碼（Speculative Decoding）

讓較小模型先草擬幾個 token，之後再由大模型驗證。

- 草擬頭預測可能的下一個 token
- 大模型檢查候選 token
- 正確的 token 可快速接受
- 錯誤的 token 會被拒絕並重試

核心概念：
- 快速的小模型提前猜測
- 大模型只驗證這些猜測
- 因此能降低每個 token 的延遲

適合使用於：
- 互動式 AI 系統
- 對首 token / 每 token 延遲敏感的任務

## 6) 張量與專家並行（Tensor & Expert Parallelism）

將模型權重或專家層切分到多張 GPU 上。

- 張量平行：把一層矩陣切分到多張 GPU
- 專家平行：將專家分散到多張 GPU
- 不同裝置可同時計算不同部分

核心概念：
- 在多張 GPU 上擴展推理
- 降低記憶體壓力並提升吞吐量

適合使用於：
- 非常大的模型
- 多 GPU 集群
- 記憶體需求高的部署

## 7) 解耦式服務（Disaggregated Serving）

將生成的兩個主要階段拆分到不同 GPU pool。

- Prefill GPU：讀取 prompt 並計算初始上下文
- Decode GPU：逐個生成 token
- 每個階段可獨立擴展

核心概念：
- Prefill 和 decode 有不同瓶頸
- 分開服務可避免其中一個階段拖慢另一個

適合使用於：
- 大規模推理系統
- Prompt 處理與生成需求差異明顯的工作負載

## 什麼情況適用哪個？

| 情境 | 建議技術 |
|---|---|
| 模型太大，放不進你的 GPU | 1、2、6 |
| 每個 token 都太慢 | 5、1、6 |
| 首 token 太慢 | 3、7 |
| 太多人在排隊等待 | 4、7、3、1 |

## 簡短總結

這些技術都針對 LLM 服務中的不同瓶頸：

- 量化：降低記憶體使用量
- 蒸餾：減少模型大小
- 前綴快取：重用計算
- 連續批處理：提升吞吐量
- 推測解碼：降低延遲
- 平行化：跨 GPU 分散工作
- 解耦式服務：分離階段以便擴展

## 結論

如果你想讓 LLM 更快，通常你需要優化以下其中一個方向：

1. 記憶體佔用
2. 重複計算
3. 批處理效率
4. 每 token 延遲
5. 多 GPU 平行處理
6. 系統層級的服務結構

每種優化都有不同效果，因此最佳選擇取決於你真正遇到的瓶頸：

- GPU 記憶體不足
- 首 token 延遲過高
- token 生成速度過慢
- 請求併發過多
